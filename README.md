# Operator: Reality

Адаптивный наблюдатель для Minecraft Java 26.3 + Fabric.

**Текущая версия:** 0.14.0  
**Рабочая ветка:** operator-dev  
**Репозиторий:** https://github.com/craftkot/ytr

## Возможности 0.14.0

- Пассивное наблюдение мира первые 24 000 игровых тиков.
- Отдельная память игроков по UUID; офлайн-время не засчитывается.
- Запись маршрутов, дистанции, истории добычи и направлений.
- Ограниченная карта последних 4 096 воздушных ячеек на игрока.
- Раздельное происхождение ячеек: добыто игроком или обнаружено локальным сканером.
- Автоматическое обнаружение ранее существовавших тоннелей и пещер рядом с игроком.
- Сканирование запускается, если ячейка ног или головы имеет не менее двух соседних блоков с полной коллизионной формой либо хотя бы один такой блок и находится минимум на 6 блоков ниже локальной поверхности по heightmap. Это позволяет начинать поиск и в центре большой подземной пещеры.
- Flood-fill по шести направлениям в ограниченном объёме 25×25×10 блоков.
- До 4 096 проверяемых позиций на один скан; одновременно выполняется не более 16 сканирований; глобальный бюджет — до 128 позиций за серверный тик.
- Сканер не загружает чанки принудительно и не сканирует выгруженные области.
- Обнаруженные воздушные ячейки не перезаписывают доказательства добычи.
- При заполнении лимита сначала вытесняются старые ячейки, найденные сканером; добытые игроком ячейки имеют приоритет.
- Высотно-зависимая 3D-сеть: тупики, развилки, вертикальные шахты, циклы и изолированные участки.
- Фоновая проверка до 128 сохранённых ячеек за тик; занятые ячейки удаляются из карты.
- Атомарное сохранение профилей; схема памяти 8 сохраняет планировщик, строительную карту, BlockState и счётчики комнат без сброса прежних наблюдений.
- Детерминированное ядро решений оператора: классификация поведения игрока (MINER / EXPLORER / CAVER / BUILDER / MIXED).
- Выбор теневого плана вмешательства по фактическим данным: TUNNEL_FOLD, PATH_ECHO, DEPTH_LURE или DIMENSION_DRIFT.
- Двойной допуск к планированию: завершение 24 000 мировых тиков и 24 000 активных тиков конкретного игрока.
- Пересмотр решения раз в 200 игровых тиков; смена плана ограничена cooldown в 6 000 тиков.
- Команда `/operator brain` показывает фазу, поведенческий профиль, план, уверенность и причину выбора.
- Отслеживание размещённых блоков через подтверждение фактического изменения мира после использования BlockItem.
- Раздельная память построек каждого игрока, включая координаты, измерение, ID блока, сериализованные свойства BlockState и время установки.
- Удаление записи о строительном блоке при его разрушении любым игроком, включая творческий режим.
- Проверка до 64 сохранённых строительных ячеек за серверный тик в уже загруженных чанках; обнаруживает исчезновение блоков после взрывов, поршней и внешней замены.
- Ограниченная история до 8 192 размещённых блоков на игрока; анализ компонентов выполняется не чаще одного раза в 20 тиков на игрока и не более одного профиля за серверный тик.
- Поиск связных компонентов по шести соседним направлениям с разделением по измерениям.
- Геометрическая классификация компонентов от 8 блоков как структур; от 24 блоков и габаритов не менее 3×3×3 — как кандидатов на постройки.
- Метрики размера, габаритов, разнообразия блоков и эвристической уверенности; строительный профиль влияет на выбор стратегии оператора.
- Снимок BlockState сохраняет свойства ориентации, половины двери, открытого состояния, формы ступени и другие доступные свойства; аудит обновляет их без ложного увеличения числа размещений.
- Геометрический анализ оболочки: покрытие пола, крыши и четырёх стен.
- Подсчёт дверей (нижняя половина — одна дверь), стеклянных блоков/панелей, лестниц и плит.
- Выявление внутренних горизонтальных этажных плоскостей отдельно от периметра стен.
- Flood-fill пустых ячеек в ограниченном AABB для оценки замкнутого внутреннего объёма; не более 32 768 ячеек на компонент и 65 536 суммарно за анализ одного профиля.
- Разделение типов `ENCLOSED_BUILDING`, `OPEN_BUILDING`, `BUILDING_CANDIDATE` и `STRUCTURE`; это геометрические категории, не семантическое понимание назначения здания.
- Команда `/operator structures` показывает текущие постройки и три крупнейших компонента.
- Внутри замкнутых компонентов выделяются отдельные непрерывные объёмы воздуха: кандидаты на комнаты (до 128 на компонент).
- Двери между разными замкнутыми объёмами образуют рёбра графа комнат; внешняя дверь не считается внутренним соединением.
- По соседству со свободными ячейками распознаются кровати, хранилища, рабочие блоки и печи; комнатам назначаются предварительные роли BEDROOM/STORAGE/WORKSHOP/SMELTERY/MIXED/UNCLASSIFIED.
- Подтверждённые размещения двухблочных дверей и кроватей дополнительно проверяют соседнюю ячейку, которая была воздухом до установки.
- Команда `/operator rooms` показывает не более пяти комнат и пяти дверных связей в текущем измерении, а также суммарные счётчики.
- Команда `/operator snapshot` по явному запросу игрока записывает защищённый контрольной суммой снимок ближайшей связной постройки.
- Для записанных блоков фиксируются текущие BlockState и полные NBT блок-сущностей (включая содержимое контейнеров); снимок сохраняется атомарно в папке мира, отдельно от памяти наблюдателя.
- Команда `/operator preview <x> <y> <z>` проверяет допустимость предполагаемого переноса последнего снимка, не перемещая ни одного блока.
- Предварительная проверка запрещает пересечение старой и новой областей, выход за высоту/границы мира, выгруженные чанки, занятые назначения и изменения источника после снимка.
- Команда `/operator transaction prepare <x> <y> <z>` сохраняет полный журнал BEFORE-состояний обеих областей, включая воздух, естественный рельеф и NBT.
- Команда `/operator transaction status` читает последний журнал с проверкой SHA-256, не выводит NBT в чат.
- Новый `RecoveryPlanner` сопоставляет текущий мир с BEFORE-образом журнала и ожидаемым AFTER-образом гипотетического переноса целой области.
- Команда `/operator transaction audit` анализирует загруженные блоки и фиксирует несоответствия, недоступные чанки и возможные следы частичного переноса без изменений мира.
- В версии 0.14.0 каждая проверка recovery audit записывает хеш-связанное состояние в отдельный checkpoint-файл, сохраняемый атомарно.
- Команда `/operator transaction checkpoint` читает последний проверенный checkpoint после перезапуска сервера.
- Read-only адаптер Minecraft извлекает актуальные BlockState и NBT только из уже загруженных чанков.
- Ограниченный анализ соседних блоков и полного источника/назначения помечает жидкости, механизмы, гравитационные и зависимые блоки как риски.
- Абстрактный RecoveryExecutor поддерживает callback до/после отдельной записи и тестируется на имитированных прерываниях, без реального изменения чанков.
- Абстрактный `RecoveryExecutor` использует compare-and-restore, повторную проверку состояния и идемпотентное восстановление; тестируется на имитированном мире с искусственным прерыванием.
- Откат в реальном Minecraft ещё **не разрешён**: адаптера безопасной записи блоков/NBT нет.

## Construction Intelligence

Система запоминает не все блоки мира, а только блоки, которые игрок, вероятно, разместил сам: при взаимодействии с гранью блока оператор проверяет, держит ли игрок BlockItem и была ли соседняя позиция воздушной. На следующем серверном тике позиция проверяется повторно. Если там действительно появился блок, в персональную карту записываются координаты, измерение, ID блока и сериализованное состояние BlockState.

Состояние блока содержит доступные свойства вроде направления, верхней/нижней половины двери, открытого состояния, формы ступени и waterlogged. Фоновый аудит обновляет свойства без повторного учёта размещения. Разрушение ранее записанного блока удаляет его из карты независимо от того, кто сломал блок. Размещения в творческом режиме также учитываются.

После изменений оператор с ограниченным бюджетом пересчитывает связные компоненты по шести граням и отдельно по измерениям:
- от 8 связанных блоков — распознанная структура;
- от 24 блоков и габаритов минимум 3×3×3 — геометрический кандидат на постройку;
- покрытие нижней и верхней плоскостей оценивается как пол и крыша;
- четыре вертикальные стороны дают оценку стен;
- ID блоков используются для подсчёта дверей, стекла/стеклянных панелей, лестниц и плит;
- горизонтальные плоскости внутри периметра анализируются как возможные этажи;
- flood-fill пустых ячеек в ограниченном объёме оценивает замкнутую часть внутреннего пространства.

Категории `ENCLOSED_BUILDING`, `OPEN_BUILDING`, `BUILDING_CANDIDATE` и `STRUCTURE` основаны только на геометрии размещённых блоков. Внутренний flood-fill ограничен 32 768 ячейками на компонент и 65 536 ячейками суммарно за один анализ профиля; слишком большой объём помечается как не проанализированный, а не сканируется без лимита. Команда `/operator structures` показывает метрики трёх крупнейших компонентов. История хранит максимум 8 192 блока на игрока, анализируется не более одного профиля за тик и не чаще раза в 20 тиков на профиль.

Это не полный скан мира и не семантическое понимание здания. Замкнутые пустоты вычисляются только по записанным размещениям: естественные блоки, пропущенные события установки, комнаты, которые соединены с внешним пространством, могут исказить оценку. Команды, WorldEdit, генераторы и некоторые модифицированные способы установки блоков не попадают в журнал. NBT блок-сущностей и содержимое контейнеров пока не сохраняются.

## Room Intelligence — граф помещений (0.10.0)

Анализатор использует **только историю реально зафиксированных размещений**. Внутри габаритов связной постройки он сначала отделяет воздух, соединённый с внешним краем, от замкнутых пустот. Затем flood-fill по шести направлениям делит оставшиеся пустые ячейки на комнаты. Двери считаются разделяющими блоками даже в открытом состоянии; если по обе стороны двери есть две разные замкнутые комнаты, создаётся связь между ними.

Назначение каждой комнаты определяется эвристически: по соседним кроватям, хранилищам, рабочим блокам и печам. Несколько равносильных признаков дают MIXED, отсутствие признаков — UNCLASSIFIED. Это не компьютерное зрение и не обученная нейросеть.

Бюджеты: до 32 768 ячеек на компонент, до 65 536 ячеек суммарно на профиль за проход, максимум 128 комнат и 128 дверных связей на компонент. При превышении лимита анализ помечается неполным; неизвестные помещения не выдумываются.

Команда `/operator rooms` выводит граф для текущего измерения. Память хранит суммарное число комнат, внутренних дверных связей, комнат с выявленными функциональными признаками и размер наибольшей комнаты. Эти показатели используются только для теневого плана HOME_ECHO, ничего не меняющего в мире.

Ограничение: **отсутствие записи о блоке не означает воздух в реальном мире**. Часть построек, созданных командами/другими модами/до установки мода, может быть ошибочно сегментирована; природные блоки, открытые дверные проёмы без дверей, фактическая коллизия мебели и открывание дверей не учитываются как полноценная навигация. NBT и содержимое контейнеров не записываются.

## Snapshot & relocation preflight (0.11.0)

**`/operator snapshot`** — создаёт снимок ближайшей к игроку связной постройки, состоящей только из ранее отслеженных размещённых блоков. Нужно находиться не дальше 48 блоков от такого компонента. Максимум 4096 записанных блоков. В момент снимка сервер повторно проверяет каждый блок: исходные чанки должны быть загружены, а типы блоков должны совпадать с памятью. Для каждого блока сохраняются полный BlockState и NBT блок-сущности через `saveWithFullMetadata`, если такая блок-сущность есть. При любой ошибке снимок полностью отклоняется.

Снимок получает UUID и SHA-256 от координат, свойств и NBT. Запись происходит в новый файл через временный файл и атомарное перемещение: `<мир>/operator_reality/snapshots/<UUID игрока>/<UUID снимка>.json`. Не более 8 снимков на игрока, 4 МиБ на файл; 256 КиБ NBT на один блок и 2 МиБ суммарного NBT. Предыдущие файлы не перезаписываются. NBT может содержать инвентарь и личные данные; файлы предназначены только для администратора сервера, данные NBT не публикуются в чате.

**`/operator preview <x> <y> <z>`** — берёт последний сохранённый снимок игрока и интерпретирует `x y z` как будущую минимальную координату объёма постройки. Проверяет: текущий источник и его NBT всё ещё совпадают со снимком, исходные и целевые чанки загружены, назначения всех отслеженных блоков пусты, смещение не превосходит 4096 блоков на ось, старый и новый AABB не пересекаются, а границы мира и высота допустимы.

`PREVIEW_ONLY` означает только прохождение проверок. Система **не** перемещает дом, не изменяет чанки, не удаляет исходные блоки и не обещает полноценную безопасность. Она пока не сохраняет воздух/природные блоки вокруг постройки, не проверяет физику, крепления, других игроков и мобов, соседний редстоун, взаимодействие других модов и поддержку блоков. Исполнять такой перенос до создания журнала операций с полными данными и обратимым применением нельзя.

## Подготовка транзакций (0.12.0)

После `/operator snapshot` и успешного `/operator preview <x> <y> <z>` команда `/operator transaction prepare <x> <y> <z>` перечитывает актуальный снимок и проверки, затем фиксирует **каждую** ячейку в ограниченных прямоугольных областях источника и назначения. В журнал включены координаты, типы блоков, BlockState и, при наличии, BlockEntity NBT. Это позволяет позже построить план обратного восстановления даже для неотслеженных обычных блоков и воздуха.

Проверяются границы мира, загруженность чанков, отсутствие пересечений, целостность снимка, изменения источника, занятость полного целевого объёма. Отличие от прежнего preview: для подготовки журналов **вся** область назначения должна быть пустой, не только координаты известных размещённых блоков.

Лимиты: до 4096 ячеек в одной области и 8192 суммарно; 256 КиБ NBT на одну блок-сущность, 2 МиБ суммарно; не более 8 МиБ на журнал и 4 журналов на игрока. Журнал сохраняется новым отдельным файлом в `<мир>/operator_reality/transactions/<UUID игрока>/<UUID журнала>.json`. Старые журналы не перезаписываются, NBT в игровой чат не выводится.

`/operator transaction status` читает последний корректный журнал, проверяет SHA-256 и показывает число защищённых ячеек и состояние `PREPARED`. Списки обратных состояний пока доступны только внутри кода и тестов; **команды применения, отката и восстановления после сбоя ещё не реализованы**. Подготовленный журнал не является гарантией безопасности будущего переноса: соседние структуры, сущности, физика и сторонние моды требуют отдельных проверок.

## Recovery Engine — аудит и тесты отката (0.13.0)

Команда `/operator transaction audit` читает **последний** журнал PREPARED, обязательно проверяет его SHA-256 и сравнивает сохранённые исходные и целевые блоки с текущим миром без принудительной загрузки чанков. Для каждого блока допустимы два состояния:

1. `BEFORE`: точное исходное состояние из журнала — блок не изменён.
2. `AFTER`: строго ожидаемое состояние модели переноса *всего* исходного AABB в целевой AABB; исходные ячейки становятся обычным воздухом.

Посторонние значения дают `CONFLICT`, выгруженные ячейки — `UNLOADED`, полностью исходное состояние — `UNCHANGED`, а совпадение части блоков с моделью AFTER — `RESTORE_NEEDED`. Ни при одном результате команда ничего не записывает в мир. Эти состояния **не являются доказательством**, что перенос действительно выполнялся: такая же картина могла возникнуть из-за обычного строительства.

Для тестирования добавлен независимый от Minecraft `RecoveryExecutor`. Он принимает абстрактный мир с атомарной операцией `compareAndRestore`, сначала проверяет **все** ячейки и запрещает любую запись при конфликте. Успешно исправленные позиции после имитированного сбоя пропускаются на следующем запуске; после полного выполнения состояние проверяется повторно. Тесты моделируют частичный перенос, повторный запуск, принудительное прерывание, чужие изменения, выгруженные ячейки и некорректное смещение.

**Ограничения безопасности:** если исходная область содержит BlockEntity NBT (сундуки, печи и т.п.), планировщик восстановления возвращает `UNSUPPORTED_BLOCK_ENTITY`, поскольку NBT часто содержит координаты и дополнительные ссылки. Неполные и повреждённые журналы блокируются; для повреждённого последнего журнала запрещён автоматический переход к более старому. SHA-256 здесь обнаруживает случайные повреждения, но не защищает от злоумышленника, контролирующего файлы сервера. **В игровом моде нет команды выполнения отката, автоматики восстановления или реального переноса.**

## Recovery Checkpoints & Boundary Safety (0.14.0)

**`/operator transaction prepare <x> <y> <z>`** после сохранения полного PREPARED-журнала создаёт дополнительный checkpoint #0. Хранение: `<мир>/operator_reality/recovery/<UUID игрока>/<UUID журнала>.json`. Checkpoint привязан к SHA-256 исходного журнала и UUID владельца; цепочка каждого следующего события содержит хеш предыдущего.

**`/operator transaction audit`** по-прежнему ничего не меняет, но теперь записывает результат в checkpoint-файл: `UNCHANGED`, `RESTORE_NEEDED`, `CONFLICT`, `UNLOADED` или `UNSUPPORTED_BLOCK_ENTITY`. Также выводит ограниченный отчёт о рисках в захваченных областях и одно-блочной окрестности обеих AABB. При превышении бюджета окрестности (8192 позиции) анализ помечается неполным вместо неограниченной прогрузки чанков.

**`/operator transaction checkpoint`** позволяет после перезапуска увидеть записанный результат, число проверенных блоков, конфликты и последние 12 символов хеша. Максимум 128 событий на журнал, максимум 1 МиБ на файл. Повреждённый checkpoint не перезаписывается и не считается пригодным для восстановления.

**`RecoveryExecutor`** теперь принимает callback, вызываемый непосредственно *до* и *после* каждой сравниваемой записи; тесты моделируют отказ записи checkpoint и корректное повторное прохождение без повторного восстановления уже исправленных блоков. В этой версии callback использован только в тестовом мире, а игровой адаптер предоставляет **только чтение**. Никаких фаз `APPLYING`, реальных операций записи и команды отката в Minecraft пока нет.

Нулевое количество выявленных опасных блоков **не означает**, что перемещение безопасно: инспектор не моделирует соседний редстоун, состояние сущностей, тики блоков, сторонние моды и полную физику. Журналы с BlockEntity NBT по-прежнему не разрешаются к восстановлению. SHA-256 фиксирует случайные изменения и ошибки записи, но не защищает от злоумышленника с доступом на запись файлов сервера.

## Как работает локальное обнаружение воздуха

Оператор не сканирует весь мир. Каждые 100 игровых тиков он может запустить локальный поиск около игрока. Для старта хотя бы одна из двух ячеек на уровне ног или головы должна быть воздушной и либо иметь два соседних полных коллизионных блока, либо находиться минимум на 6 блоков ниже локальной поверхности при наличии хотя бы одного такого соседа. Это снижает риск сканирования открытого неба и обычной поверхности.

После старта выполняется ограниченный flood-fill по шести граням блока. Область ограничена 12 блоками по горизонтали в каждую сторону, 6 блоками вниз и 3 блоками вверх от точки старта. Сканер проверяет только уже загруженные позиции. Работа распределяется между тиками, а при большом числе игроков используется общий бюджет 128 проверок за тик.

Обнаруженные ячейки сохраняются отдельно от добытых. Если игрок позже ставит блок в найденную воздушную ячейку, аудит удаляет её. Если в ранее добытом месте снова появляется блок, оно также удаляется.

## Ограничения и честные границы

- Construction Intelligence видит только подтверждённые размещения через BlockItem; команды, WorldEdit, генераторы и часть модифицированных способов установки блоков не отслеживаются. В 0.10.0 добавлено подтверждение второго блока двери и кровати при обычной установке.
- Геометрический кандидат не обязательно является домом: назначение комнат, меблировка, функциональные блоки и пригодность помещения не определяются.
- Сериализованные BlockState и NBT блок-сущностей записываются вручную через команду snapshot, а полные AABB-образы через transaction prepare; фактическое восстановление и перенос построек пока не реализованы.
- Это локальное обнаружение доступных воздушных пространств, а не полный сканер мира.
- Игрок должен находиться внутри тоннеля/пещеры или рядом с достаточно закрытым воздушным участком.
- Большие пещеры могут быть обрезаны пределом 4 096 посещённых позиций на один проход.
- Выгруженные чанки пропускаются; сканер не вызывает их загрузку.
- Воздушные полости далеко от игроков не обнаруживаются.
- Разрушения взрывами и другими системами попадут в карту только если игрок окажется рядом и локальный сканер сможет пройти к новой полости.
- Сканер не различает рукотворную шахту и природную пещеру: он фиксирует геометрию доступного воздуха, а не происхождение каждого блока.
- 3D-реконструкция всё ещё послойная: центр-линии вычисляются отдельно по Y и соединяются в трёхмерный граф. Это не полный 3D medial-axis transform.
- Ядро решений пока только формирует и сохраняет планы; оно не исполняет их.
- Изменение биомов, перестройка построек, перемещение мобов и изменение координат ещё не реализованы.
- Автоматическое копание, установка блоков и перестройка мира выключены.

## Команды

    /operator status
    /operator brain
    /operator structures
    /operator rooms
    /operator snapshot
    /operator preview <x> <y> <z>
    /operator transaction prepare <x> <y> <z>
    /operator transaction status
    /operator transaction audit
    /operator transaction checkpoint
    /operator profile
    /operator tunnels
    /operator network
    /operator network2d

- status — фаза наблюдения, число профилей, добытые и обнаруженные воздушные ячейки, активные сканирования, планы и бюджеты.
- brain — состояние планировщика текущего игрока: поведенческий профиль, план вмешательства, уверенность и причина выбора.
- structures — анализ связных построек в текущем измерении, габариты и кандидаты на здания.
- rooms — замкнутые геометрические комнаты, дверные связи и предварительные функциональные роли.
- snapshot — вручную создать целостный снимок ближайшей отслеженной постройки, включая NBT.
- preview — проверить целевые координаты для снимка без модификаций мира.
- transaction prepare — записать полный журнал BEFORE-состояний источника и пустого назначения без изменений мира.
- transaction status — показать последний валидный журнал без публикации содержимого NBT.
- transaction audit — сравнить журнал с загруженными блоками, вывести риски соседних блоков и сохранить проверенный checkpoint без изменения мира.
- transaction checkpoint — показать последний сохранённый checkpoint и проверить его целостность после перезапуска.
- profile — персональная статистика, включая добытые и обнаруженные ячейки.
- tunnels — связные компоненты сохранённых воздушных ячеек.
- network — высотно-зависимый 3D-граф.
- network2d — прежняя горизонтальная проекция X/Z для сравнения.

Команды brain, structures, rooms, snapshot, preview, transaction, profile, tunnels, network и network2d нужно выполнять от имени игрока.

## Сборка

Требования: Minecraft Java 26.3, Java 25, Fabric Loader 0.20.1+, Fabric API 0.165.2+26.3 и Gradle 9.8.2.

    gradle clean test build

Запуск тестового клиента:

    gradle runClient

Готовые JAR-файлы появятся в build/libs/.

## Хранение и миграция

    <папка мира>/operator_reality/operator-memory.json

Схема 4 добавляет происхождение воздушных ячеек, схема 5 — состояние планировщика, схема 6 — карту размещённых блоков, схема 7 — сериализованные BlockState и метрики оболочки/внутреннего объёма, схема 8 — счётчики комнат и дверных связей. При миграции со схемы 6 старые записи сохраняются, новые свойства BlockState первоначально пусты, а строительный анализ запускается повторно.

Перед тестированием на важном мире сделайте резервную копию.
